# Проблема с T32 — порт Devil May Cry 1 с PS2 на ПК

## В общем, расклад такой

Мы делаем **нативный PC-порт Devil May Cry 1** (версия для PlayStation 2) на чистом C под x86_64 Windows. Это **не эмулятор, не мод, не инжект** — движок переписывается с нуля, с оригинального диска читаются только ассеты. Данные диска лежат в `E:\DATA`.

Порт уже неплохо продвинулся, но мы застряли на одном конкретном месте и бьёмся в него несколько дней. Нужна твоя помощь — точная формула развёртки VRAM.

## Что уже работает идеально

На диске два формата текстур:

- **`.TM2`** (22 файла) — **полностью разобран, работает идеально, проверено глазами.** Логотип Capcom, иконки интерфейса — всё рендерится чётко, пропорции правильные, палитра на месте. Формат закрыт.
- **`.T32`** (125 файлов) — текстуры интерфейса: экран выбора, полоски здоровья, портреты персонажей, шрифты. **Вот на этом мы и увязли.**

Важный момент: TM2 на этом диске хранится **линейно** (пиксели идут строка за строкой) — поэтому он и заработал сразу. А T32 — нет.

## Что точно известно про T32 (замерено по всем 125 файлам)

Контейнер разобран полностью, арифметика сходится на каждом файле, тут ошибок нет:

```
0x00 u32  record_count      — число записей
0x04 u32  raster_size       = (u32 >> 16) << 8   — размер растра в байтах
0x08 u32  table_end         — конец таблицы записей
0x0C u32  payload_size      — растр плюс хвостовые пакеты

raster_offset = filesize - payload_size - 0x400
CLUT          = последние 0x400 байт (256 записей по 4 байта, BGRA)
```

Тождество `raster_offset + raster_size + (payload_size - raster_size) + 0x400 == filesize` выполняется на **всех 125 файлах**. Геометрия контейнера закрыта.

**Высота растра = 256 пикселей у всех файлов.** Проверено: `raster_size / width == 256` везде без исключения.

**Ширина** берётся из GS-регистра `TRXPOS`, поле `DSAX`:
- `COLBAR_F / SELECT / OP_DANTE` → 896
- `MSG_TEX` → 768
- `T_MOJI_F` → 512
- `P_MOJI_F` → 256
- `OP_MOJI` → 128

Например `0x38000 / 896 = 256` — сходится идеально.

## Вот реальный дамп COLBAR_F.T32

Размер файла: `0x385E0` (230880 байт)

Заголовок:
```
0x00: record_count = 1
0x04: 0x03800040 → raster_size = 0x38000 (229376 байт = 896 × 256)
0x0C: payload_size = 0x00038100 (229632 байт)
       растр 0x38000 + палитра 0x100 = 0x38100
raster_offset = 0x385E0 - 0x00038100 = 0x4E0
clut_offset   = 0x385E0 - 0x400 = 0x381E0
GS-пакеты: область 0x40 .. 0x4E0 (1184 байта)
```

Таблица записей (1 запись, 0x10 байт):
```
0x10: 01 00 01 00  00 00 00 00  00 00 00 00  01 00 00 00
```

Первые байты растра (смещение 0x4E0):
```
0x4E0: D2 D2 D2 D2 D2 D2 D2 D2  D2 D2 D2 D2 D2 D2 D2 D2
0x4F0: D2 D2 D2 D2 D2 D2 D2 D2  D2 D2 D2 D2 D2 D2 D2 D2
```
(Сплошные D2 — похоже на индекс фона/прозрачного цвета.)

Палитра CLUT (первые записи, 4 байта каждая):
```
0x381E0: DD 1D 14 80  04 6F B0 80  0C 6C AA 80  57 57 57 80
         64 63 0A 80  08 72 B0 80  1F 16 80 41  68 64 80
```

GS-пакеты преамбулы (начиная с 0x40):
```
0x40: 50 00 00 00 00 00 00 00   (REGISTER 0x50 — BITBLTBUF, данные нулевые)
0x48: 51 00 00 00 00 00 00 00   (REGISTER 0x51 — TRXPOS, данные = 0x03800040)
0x50: 52 00 00 00 00 00 00 00   (REGISTER 0x52 — TRXREG, данные = 0)
0x58: 53 00 00 00 00 00 00 00   (REGISTER 0x53 — TRXDIR, данные = 0)
```

**Ключевое наблюдение:** регистры `BITBLTBUF (0x50)` и `TRXREG (0x52)` — **нули**. Ни формата (PSM), ни ширины буфера, ни размеров там не записано. Данные несёт только `TRXPOS (0x51)`, и то это DSAX=896, то есть координата назначения в VRAM, а не ширина текстуры. Значит движок не конфигурирует пересылку — он просто DMA'ит готовый payload в VRAM как есть.

## В чём именно проблема

Если читать растр **линейно** (байт за байтом как индексы палитры), получается горизонтальная полосатая каша. Не узнаваемое изображение, а шум полосами — на всех T32 одинаково.

Тот факт, что растр лежит между GS-пакетами пересылки (`BITBLTBUF/TRXPOS/TRXREG/TRXDIR`), означает: **растр — это не битмап, а блок пересылки в раскладке VRAM PS2 GS формата PSMCT8 (8-bit tiled/swizzled)**. Линейное чтение эту раскладку уничтожает.

### Как мы убедились, что это именно swizzle, а не linear

Написали метрику: средний перепад яркости между соседними пикселями. У правильной раскладки соседние пиксели похожи, перепад маленький; у шума — большой.

| Раскладка | Метрика связности |
|-----------|-------------------|
| Linear (width=896) | ~1.3 – 15.5 |
| Swizzle (разные ширины) | ~0.3 – 4.2 |

Swizzle стабильно **в разы лучше** linear. Направление верное — свизл тут точно есть. Не хватает точной формулы развёртки.

## Что уже перепробовали и почему не взлетело

### Попытка 1: таблица постраничного свизла (из фанатского визуализатора)

Взяли постраничную схему из «GS Memory Swizzle Visualizer» (TellowKrinkle):
- страница = 128×64 пикселя = 8192 байта
- 32 блока по 16×16 пикселей
- `pageSwizzle` (порядок как в PSMCT32) × `columnSwizzle` (порядок PSMT8)

Написали `tools/swz_test.c` — проверку, что таблица является точной перестановкой 0..8191. Результат: `filled=8192, unique=8192, дублей нет, пропусков нет` — **БИЕКЦИЯ ОК**.

**Но картинка всё равно каша.** Таблица — перестановка, но не та перестановка, что у реального PS2 GS. Главное подозрение: для 8-битного формата блоки должны быть **16×32**, а не 16×16.

### Попытка 2: каноническая формула из ps2-tim2-tool

Нашли `unswizzle8_ps2` в рабочем конвертере `ps2-tim2-tool`:

```c
block_location  = (y & ~0xf) * width + (x & ~0xf) * 2;
swap_selector   = (((y + 2) >> 2) & 1) * 4;
posY            = (((y & ~3) >> 1) + (y & 1)) & 7;
column_location = posY * width * 2 + ((x + swap_selector) & 7) * 4;
byte_num        = ((y >> 1) & 1) + ((x >> 2) & 2);
si              = block_location + column_location + byte_num;
dst[y*width+x]  = src[si];
```

**Результат:** лучше чем linear — появляется структура (блоки, строки элементов). Но чистого изображения нет. Подозреваем, что формула рассчитана на другой stride, либо ширина у нас не та.

### Попытка 3: подбор ширины через проверку биекции

Написали `tools/t32_width.c` — ищем ширину, при которой каноническая формула даёт биекцию. Результат: **бьюкция получается при любой ширине кратной 16**. Тест не различает ширину, заход в тупик.

### Попытка 4: интерактивный тюнер

Сделали окно `dmc_tune`, где человек листает раскладки клавишами A/D и выбирает глазами. Ответ пользователя после полного перебора: **«везде каша, ничего узнаваемого»**.

## Самый важный факт — цветная шкала

`COLBAR_F.T32` — это буквально **color bar**, тестовая таблица из вертикальных цветных полос. При правильной развёртке на выходе **обязаны** получиться чистые вертикальные столбцы постоянного цвета. Это идеальный эталон — тут невозможно промахнуться, либо полосы ровные, либо нет.

На текущих формулах мы получаем вертикальные столбцы с периодом ровно **128 пикселей** (= ширина одной свизл-страницы). То есть страницы раскладываются, но порядок байтов **внутри страницы** всё ещё неверный.

## Что конкретно нужно

**Точная побитовая формула развёртки (deswizzle) VRAM PS2 GS для формата PSMCT8 (8-bit indexed).**

Что известно:
- страница = 128×64 пикселя = 8192 байта
- для 8-битного формата страница делится на блоки **16×32 пикселя** (не 16×16)
- один байт = один пиксель
- ширина строки (VRAM pitch) для COLBAR_F = 896, высота = 256

Ищем формулу эквивалентную макросам `GSOffset8Page / GSOffset8Col / GSOffset8Row` из старого софт-рендерера PCSX2, то есть:

```
offset = GSOffset8Page(x, y) × 8192 + GSOffset8Col(x, y) + GSOffset8Row(x, y)
```

или замкнутую формулу `si(x, y)`, которая переводит линейные координаты (x, y) в байтовое смещение в VRAM.

**Критерий правильности:** после применения к растру COLBAR_F должны получиться чистые вертикальные цветные полосы, а не артефакты с периодом 128.
